## 2. Interface — `client/kernel/render-api/`
Files: `interface.js` (contract + validators + pure-JS `composeMat4`/`decomposeMat4`, **no three**) · `three-backend.js` (backend #1 + `createBackend(name)` registry; engine config `renderBackend`, default `'three'`).
Handles = integers (0 = none/root). Matrices = column-major 16-number arrays. All args plain data.
- geometry: `createMesh({positions,normals?,uvs?,indices?})` · `destroyMesh`
- material: `createMaterial(params, textures?)` (pbr fields + `preset:<name>`; textures = rgba8 `{width,height,data,srgb}`) · `destroyMaterial`
- scene: `createNode(mat4,parent)` · `createInstance(mesh,material,mat4,flags{parent,castShadow,receiveShadow,visible,renderOrder,euler,tags})` · `updateNode` · `removeNode`
- camera/lights: `setCamera(view,proj)` · `setSun{direction,color,intensity,castShadow}` · `addPointLight/updatePointLight/removeLight`
- frame: `renderFrame(dt)` · `resize(renderHeight)` · `dispose()`
Three-only TRANSITIONAL adapters (listed in `capabilities`; not for neutral code): `createMeshFromRecipe(part)` (tessellation still in geometry.js), `adoptNode(Object3D)`, `nativeNode(id)`.
**Routed this round (R1)**: static level mesh parts in `View.applyMesh` (view.js) → `createMeshFromRecipe`+`createMaterial`+`createInstance` under the adopted entity Group; teardown via `removeNode` (applyMesh rebuild + `View.remove`). `View` takes `{render | renderBackend}`; default = three backend. Not wired: `setCamera`, lights, `renderFrame`, `resize` (implemented + unit-tested only; kernel frame path stays authoritative).
Test: `test/render-api.test.js` (5): interface conformance, composeMat4 == THREE.Matrix4.compose, old-path vs backend parity per part (shared geometry/material identity, shadow/visible/renderOrder/userData, euler exact, matrix ≤1e-12), typed-array mesh + textures + removal, lights/camera.

## 4. Compatibility layer (games must not change)
Goal: engine update + config flip (`renderBackend: 'wgpu'`) swaps the renderer; zero game edits.
**(a) three scene graph = the game-facing scene description.** Games keep mutating three `Object3D/Group/Mesh/InstancedMesh/Light` (via `view.getGroup`, injected `three`, imports). A *scene adapter* (`render-api/scene-adapter.js`, next round) walks `scene` each frame (dirty-flag on `matrixWorld`/`visible`/material `version`/geometry attribute `version`) and emits render-api calls: new Mesh → `createMesh`(arrays from BufferGeometry attributes, deduped by geometry uuid) + `createMaterial` + `createInstance(mat4 = matrixWorld)`; InstancedMesh → instance buffer upload (needs `createInstanced(mesh,material,mat4[],count)` + `updateInstances` — add to interface); lights → `setSun`/`addPointLight`; camera → `setCamera`. three stays the CPU-side math + scene graph + loaders + animation (AnimationMixer/Skeleton evaluate in JS; adapter uploads bone matrices) — so math-only, loaders, and Object3D usage need NO emulation; the three backend adapter is the identity. Skinned meshes need a `createSkin(mesh, boneCount)` / `updateBones(Float32Array)` extension (skinning is the one scene-graph feature not yet in the interface).
**(b) Custom materials = the hard set — see §5/§6.** No shader rewrites (Pascal): game shaders are TRANSLATED by three's own node builder.
**(c) Backend choice by engine config.** `createBackend(config.renderBackend ?? 'three')`; `View` already does this. The adapter in (a) is only instantiated for non-three backends; `three` keeps its direct path (today's behaviour).

## 6. WGSL binding contract (what three's generated shaders expect) — from three r180 source (`nodes/core/NodeBuilder.js`, `renderers/webgpu/nodes/WGSLNodeBuilder.js`); NOT yet exercised on a non-three backend → UNVERIFIED
1. **Package, not a bare string.** Node builder output per (material, object, pass) = `{ vertex WGSL, fragment WGSL, bindGroups[], attributes[], varyings, outputStruct }`. Uniform *names are generated ids* (`nodeUniform<N>`, per-texture `<name>` + `<name>_sampler`), so the consumer must take binding metadata from `builder.getBindings()` (name, group order, kind, owning node), NOT guess it. The compat layer exports this as JSON next to the WGSL; naga reflection cross-checks it.
2. **Bind groups** are ordered by `UniformGroupNode.order` then re-indexed densely (`sortBindingGroups`): `frame` (shared, once/frame) · `render` (shared, once per render call) · `object` (per object/material). Group *indices are per-shader*, assigned by position — the host must read the index from the package, never hardcode 0/1/2.
3. Each group = `@group(g) @binding(b)`: one uniform struct buffer (std140-like WGSL struct layout, vec3 padded) + `texture_2d/cube/3d/storage` + `sampler`/`sampler_comparison` (shadow) + `var<storage>` buffers (read / read_write) in declaration order.
4. **Built-in nodes → where they live:** camera (`cameraProjectionMatrix, cameraViewMatrix, cameraWorldMatrix, cameraNear/Far, cameraPosition`) → `render` group, updated from the camera each render · time/delta → `frame` · object matrices (`modelMatrix, modelViewMatrix, normalMatrix, modelWorldMatrix`) → `object` group · lights (`LightsNode`: per-light position/color/distance/decay/direction/shadow data) → `render` uniform arrays; the light *set* is part of the shader cache key (kernel's 16-light pool exists because of this) · shadows → depth texture + `sampler_comparison` + light-space matrices in `render` group (CSM = N cascades) · fog → color/near/far uniforms in `render` · skinning → bind matrices + bone matrix buffer in `object` group · instancing → `instanceMatrix` as vertex attribute or uniform/storage buffer (count-dependent) · morph targets → texture/storage per object · environment/IBL → cube/PMREM texture + sampler in `render`.
5. **Vertex inputs:** `@location(n)` per geometry attribute *by name* (`position, normal, uv, uv1, color, skinIndex, skinWeight, instance*`), formats from the BufferAttribute (itemSize/normalized/type); location order = builder order, in the package. Outputs: fragment struct `@location(i)` per render-target attachment; MRT for GI/AO passes.
6. **Update model:** node values update through three's JS update loop (`updateBefore/updateFrame/updateRender/updateObject` callbacks on nodes). Backend-neutral rule: that loop keeps running in JS (it is the game-visible three), writes into the uniform byte buffers named in the package, and the buffers cross to the backend (shared memory / wasm / IPC). Compute nodes (`compute()`, `instancedArray`, `storage`) dispatch WGSL compute entry points with the same package format (GI + fluids + empire-earth raymarch depend on this).
7. Backend obligations: wgpu device features matching three's request (`float32-filterable`, `timestamp-query` optional, `texture-compression-*`), reversed-Z / depth conventions (`WebGPUCoordinateSystem`, boomtown references it), `texture_depth` + comparison sampler support, MRT, storage textures, `@builtin(instance_index/vertex_index/position/front_facing)` mapping, non-uniform control-flow limits in naga (derivatives under divergent branches — three-generated code is WebGPU-validated already, naga parity = TEST NEXT).
